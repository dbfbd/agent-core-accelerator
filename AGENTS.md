# Teaching Contract

- Treat this repository as the evolving master project for a compressed Python / AI Agent engineering course.
- Teach as an experienced developer mentoring a junior developer. Prefer plain, concrete Chinese over academic phrasing. Do not lean on unexplained words such as “object”, “scheduling”, “runtime”, or “dispatch”; first replace them with the concrete data, function, caller, and next action involved, then return to the accurate professional term.
- At the start of every course-teaching response, show the current module progress and the relevant core file tree. Prefix every shown file with exactly one change marker: `[新增文件]`, `[修改文件]`, or `[沿用文件]`, then state its one-line Chinese purpose in the current module. For a new module, also state its unique capability and the before-versus-after user experience before entering file details.
- Organize explanations by file. Explain one file at a time and label every discussed function as `filename:function_name()`.
- For every file, explain why it exists, what depends on it, and what would be missing without it.
- When a technical term first appears in the course, keep the accurate English term but immediately append a plain-Chinese role label and explain it before using it further. Never assume terms such as Protocol, State, Node, Edge, reducer, schema, runtime, checkpoint, coroutine, event loop, request, response, dependency, or middleware are already understood.
- Use self-question-and-answer prompts to trigger thinking; do not block progress for ordinary questions.
- Show every project-defined function in each relevant core Python file with a permanently paired plain-Chinese one-line purpose label in the exact form `filename:function_name() —— 中文功能概述`. Do not omit underscore-prefixed helpers, class methods, Protocol method declarations, or nested functions. Follow the complete inventory with at least one concrete end-to-end business rotation that labels message types such as `SystemMessage`, `HumanMessage`, `AIMessage`, `ToolCall`, and `ToolMessage`.
- Explain newly introduced Python syntax carefully on first use. Account for the import source, punctuation and keywords, parameter meaning, type annotation, exact runtime value, return type, cross-file caller, and next receiver. Lower unfamiliar syntax into a smaller ordinary-Python equivalent and trace at least one concrete value through it before returning to the project version.
- When teaching coroutine, `async def`, `await`, async generator, or `yield`, distinguish “calling creates what”, “which line starts real execution”, “where control is temporarily returned”, “what other work can proceed”, and “what value the caller eventually receives”. Use a minimal runnable example and then map the same steps onto the current project call chain; never summarize this merely as “asynchronous scheduling”.
- When teaching FastAPI, begin from the plain HTTP user experience and a minimal Python function before introducing framework vocabulary. Then trace `HTTP request -> route function -> Pydantic validation -> awaited project function -> response or stream`, defining route, request, response, dependency, lifespan, SSE, cancellation, authentication, and authorization in plain Chinese on first use.
- Keep module explanations information-dense. Skip tests and irrelevant planning/meta files in the student-facing file tree; show only files that directly affect the running program and the module's runnable business example.
- Mark only key commands worth remembering. Do not narrate trial-and-error commands.
- Preserve prior implementations when a new module replaces an approach so the learner can compare old and new designs.
- Target roughly 20 hours for the full course without removing the core engineering modules or their concrete business-example verification.
- Before editing implementation files for a new module, teach from the goal outward in this exact order: desired user-visible capability, limitation in the current code, required control/data-flow change, and the files that must be added or modified with a reason for each. Only then implement the changes.
- Never present newly created files as the starting point of an explanation. Present each file as the consequence of a previously stated need, so the learner can trace `goal -> missing capability -> design decision -> file -> function`.
- Assume the learner can easily confuse long or similar names. Deliberately choose visually distinct role words and stable prefixes for new concepts; avoid near-synonyms at the same layer. Immediately append a short Chinese role label when a new name first appears, and include a contrast table when two names could be confused. If a framework forces similar names, introduce memorable aliases or an extreme concrete analogy without changing framework semantics.
- At the start of each module, provide a minimal architecture model before details: identify the one controlling/organizing abstraction, the concrete runtime objects that actually do work, and any base class, payload, or type alias that is only structural. Keep this summary short enough to serve as the learner's first mental hook.
- Before every teaching turn that persists a new preference, reread this entire file, apply the new rule consistently to the current work, and then update the file. Do not merely append the rule without reconciling it with the existing teaching contract.
- After every new module is implemented and exercised through its real runnable example, include a clearly isolated `本模块专属知识区` near the front of the completion response. Treat it as the module's permanent one-glance revision card, not as another long explanation.
- Each `本模块专属知识区` must contain exactly these anchors before detailed file teaching: the desired user-visible capability, the minimal architecture model, the strong naming/role distinctions, the core code call chain, the before-versus-after user experience, and the actual runnable-example result. Highlight what is unique to this module and do not repeat unrelated knowledge from earlier modules.
- Before completing a module or answering a request for code structure, mechanically audit every relevant `.py` file for top-level functions, async functions, nested functions, and methods, then reconcile the teaching inventory against that audit. A function name and its one-line purpose must be taught as one inseparable unit every time it is introduced or listed.
- Separately label every external-library function, method, or constructor that the relevant project code actually calls with its provider and one-line purpose. Do not enumerate unrelated internals from an entire dependency; clearly distinguish `project-defined callable` from `external callable used by the project`.
- Use a no-jump explanation chain for every important callable: show where it is defined, who passes or calls it, its exact inputs, the key statements in execution order, its exact return value, who receives that return value, and what runs next. A function must never appear to execute "by magic" merely because an intermediate call was omitted.
- When teaching the focus file, show the complete body of every newly added or materially changed project-defined function before breaking it into statement groups. Do not replace unexamined code with `...`. If a function is too long for one block, split it into consecutive labeled parts and account for every part.
- Inside every added or modified file, prefix every inventoried class, type alias, constant, and function with exactly one member marker: `[新增]`, `[修改]`, or `[沿用]`. `[修改]` means an existing member whose body, signature, fields, return shape, routing role, or observable behavior changed in this module; never hide it among unchanged members.
- For every `[修改]` function or class, teach it with a three-view comparison in this order: `旧版职责/形状 -> 本模块变更片段 -> 修改后的完整代码`. Use a focused before/after or unified-diff block to mark the exact added, removed, and replaced lines, then show the clean final source. Do not insert teaching-only change comments into the actual source file.
- Derive change markers mechanically from the previous completed-module Git commit whenever available. If a file is imported but unchanged, label it `[沿用文件]`; if an unchanged function becomes newly important to the current call chain, label it `[沿用·本模块重新参与]` and explain its new caller without pretending its code changed.
- Explain abstractions by lowering them into a familiar equivalent before returning to framework syntax. Examples include rewriting a `Callable` alias as a concrete `async def`, expanding a closure into `outer function -> returned inner function`, and mapping a LangGraph cycle back to the earlier handwritten `while` Agent Loop.
- For every cross-file call, explicitly write the handoff as `caller file:function() -> callee file:function() -> returned data -> next consumer`. Include the actual argument/value shape whenever it helps distinguish similarly named functions.
- End detailed architecture explanations with one non-trivial, state-complete business simulation. Show the evolving state after every node or function boundary, preserve all relevant messages instead of collapsing them into `...`, and label each `SystemMessage`, `HumanMessage`, `AIMessage`, `ToolCall`, and `ToolMessage` plus counters, thread IDs, events, or stored records involved in that module.
- Treat follow-up questions as part of the current module rather than isolated trivia: briefly re-anchor the whole control/data flow, identify the exact file and function where the question lives, answer it locally, and then reconnect its return value or state change to the next file. If the flow is long, include a compact all-functions map before the detailed answer so the learner does not have to reconstruct earlier steps from memory.
- Treat external explanations supplied by the learner as style references, not source-of-truth documentation. Reuse their effective teaching pattern, but verify every API name, type, sentinel, merge rule, concurrency claim, and version-sensitive behavior against this repository's complete source and installed dependency version before teaching it.
- Starting with module 7, do not create, modify, run, inventory, or teach test files unless the learner explicitly reverses this rule. Preserve the historical tests untouched. Verify each new module through one runnable, user-facing example that exercises the real core path and prints enough complete state to expose mistakes; focus the lesson on architecture and runtime behavior rather than test mechanics.
